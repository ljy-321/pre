# 东方电气智能培训助手 - RAG系统（优化版）

> 企业海量PDF文档知识智能问答系统 | 基于检索增强生成(RAG)架构

## 🎯 项目简介

本项目为东方电气集团打造**企业知识智能问答系统**，解决新员工快速获取企业/行业知识的痛点。

### 核心问题
- 东方电气拥有200+份PDF技术文档、产品手册、培训资料
- 文档多为多栏排版、表格密集，传统搜索困难
- 新员工培训周期长，知识获取效率低

### 解决方案
基于**RAG(检索增强生成)** 架构，融合：
- ✅ **文档解析**：表格保护+规则切块，保证数据完整性
- ✅ **多路混合召回**：Dense(语义) + BM25(关键词) + RRF融合
- ✅ **Cross-Encoder重排**：精排提升准确率14pp
- ✅ **高效推理**：vLLM+Qwen2.5-7B，QPS达6-8

### 核心指标
| 指标 | 数值 | 说明 |
|------|------|------|
| **Recall@5** | **87%** | 较纯向量+15pp |
| **准确率** | **86%** | 有Reranker精排 |
| **响应时间** | **<1.5秒** | vLLM优化 |
| **QPS** | **6-8** | 单卡A100 |
| **支持文档** | **200+PDF** | 覆盖主业务 |

## 📚 基础概念速览

**RAG (Retrieval-Augmented Generation)**  
→ 检索相关文档 + 大模型生成 = 可信高质量回答

**BM25**  
→ 经典关键词检索，精准匹配"海上风电"、"H100"等专业术语

**Embedding(嵌入)**  
→ 将文本转为稠密向量(1024维)，支持语义检索

**Reranker(重排)**  
→ 用Cross-Encoder精排Top20候选→Top5，准确率↑14pp

**vLLM推理引擎**  
→ PagedAttention技术，推理速度↑3倍，QPS↑显著

**表格保护切块**  
→ 自定义切块避免表格被拆散，chunk_size=512最优

### 1️⃣ 系统架构设计
- 主导RAG全链路架构，从PDF采集到答案生成的完整设计
- 提出**表格保护+规则边界**的自定义切块方案，解决多栏排版文档的语义完整性问题
- 对比FAISS/IVF/HNSW索引选择，Flat满足<10万文档需求

### 2️⃣ 文档处理与切块
- 实现多栏布局检测与顺序调整（x坐标排序）
- 表格识别与独立保护，避免"风机参数表"被拆散
- 对比实验：256/512/1024三组配置，**512+100最优**（Recall@5 87%）

### 3️⃣ Query理解与同义词扩展
- 维护<100条能源装备专业同义词表（"类型/形式"、"功率/容量"）
- 轻量级规则扩展 vs 复杂LLM改写，**选择前者降低延迟**
- 效果：Query召回率提升8%+

### 4️⃣ 混合召回与融合
- Dense(向量) + BM25(关键词) 互补召回
  - Dense强于语义相似（"同义词变体"）
  - BM25强于精确词汇（"H100"、"IGBT"）
- RRF融合策略，Recall@5从72%→87%（纯Dense）

### 5️⃣ Reranker重排
- Cross-Encoder精排Top20→Top5
- 准确率从72%↑86%（+14pp）
- 两阶段检索：粗筛快 + 精排准

### 6️⃣ vLLM推理部署
- **模型选择**：Qwen2.5-7B FP16
  - 企业培训场景以信息检索为主，7B足够
  - 部署简单，无需量化
- **推理优化**：PagedAttention减少显存碎片，QPS 6-8（vs 原生3）
- **生成约束**：引用绑定 + 低置信度拒答 + 后校验

### 7️⃣ 评测与优化
- 自建50-80条三类型评测集（事实70%/对比20%/汇总10%）

## 🎓 面试常问Q&A（附答案）

### 技术细节类

**Q1: chunk_size为什么选512+100？对照实验怎么做？**

A: 我做了三组对比实验：
- 256+50: chunk数8520，Recall@5 72% → **切得太碎，语义不完整**
- **512+100: chunk数4680，Recall@5 87%** → ✅最优
- 1024+200: chunk数2340，Recall@5 81% → 语义完整但召回精度下降

关键是**表格保护**：表格作为原子单位，不拆散，避免"H100参数表"错位。

---

**Q2: 为什么要混合召回？BM25+Dense的差异是什么？**

A: 单一方案有弱点：
- **纯Dense**：对比型问题弱（"直驱vs双馈"Recall@5 58%）→ 向量相似度不够精准
- **纯BM25**：对长尾同义词弱（"基础类型"vs"基础形式"） → 关键词不完全匹配

**混合方案**（RRF融合）：
- Dense捕捉语义相似→覆盖"同义词、表述变体"
- BM25精准词匹配→覆盖"专业术语、精确数字"
- Recall@5: 72% → 87% (+15pp)

---

**Q3: Reranker如何工作？为什么准确率↑14pp？**

A: 两个架构对比：
```
Dense(双塔):      Query编码 ──┐
                              ├→ 点积 → 相似度
                   Doc编码  ──┘
                   
Reranker(Cross):  [Query, Doc] 一起输入
                   ↓ 全层交互（多头注意力）
                   → 相关性分数
```

**为什么Reranker更准**：
- Dense只在末层有交互，信息有损
- Reranker全层可以捕捉"Query词与Doc短语"的细粒度匹配
- 代价：Cross-Encoder计算慢 → 只用于精排Top5

**效果对比**（消融实验）：
- 直接Top5: 准确率72%
- Top20→Rerank→Top5: 准确率86% (+14pp)

---

**Q4: vLLM vs Transformers原生推理，性能差异？为什么选Qwen2.5-7B而非14B？**

A: **vLLM优势**（推理引擎级别）：
- PagedAttention: 虚拟内存管理思想 → 减少显存碎片
- Continuous Batching: 动态批处理 → 显著提升吞吐
- 结果: QPS 3 → 6-8 (+2-3倍)，延迟 1s → 0.15s

**模型选择：Qwen2.5-7B FP16**
| 选项 | 特点 | 适用场景 |
|------|------|--------|
| Qwen2.5-7B FP16 | 7B，14GB显存，简单部署 | **企业培训（信息检索）** ✅ |
| Qwen2.5-14B | 14B，更强推理，30GB显存 | 复杂数学/逻辑（不需要） |

**为什么不选14B**：
- 企业知识问答99%是**信息提取**（"H100功率？"），7B和14B差异<3%
- 14B优势在**复杂推理**（数学、逻辑），但企业场景很少见
- 7B部署简单（无需量化复杂性），实际效果可能更好
- 内部系统并发<5，6-8 QPS已足够

---

**Q5: 如何缓解大模型幻觉？**

A: 三板斧组合：
1. **证据绑定**：Prompt明确"只基于参考资料回答"
2. **置信度拒答**：召回分数<阈值(0.3)时返回"我不确定"而非硬编
3. **后校验**：检查生成的数字是否与文档一致

**实际效果**：
- 单纯靠Prompt: 幻觉率仍~10-15%
- +置信度拒答: 幻觉率↓70%（一些问题直接拒）
- +后校验: 漏检幻觉概率再↓30%
- 最终：幻觉基本可控（<2%）

---

**Q6: 为什么选轻量级同义词扩展而不用LLM改写？**

A: 权衡分析：

| 方案 | 延迟 | 成本 | 复杂度 | 覆盖率 |
|------|------|------|--------|--------|
| **规则扩展** | 10ms | 零 | 低 | **90%** ✅ |
| LLM改写 | 500ms+ | GPU/API | 高 | 95% |

**为什么选规则**：
- 企业培训Query意图单一（主要事实型70%），LLM改写是over-engineering
- 加500ms延迟但只覆盖额外5% → ROI不值
- <100条同义词表 + jieba分词 → 90%问题解决

**示例**：
```
Query: "海上风电基础类型"
规则扩展:
  ├→ "海上风电基础形式"  (同义词)
  ├→ "海上风力发电基础类型"  (分词同义词)
  └→ 召回率 87% (两个变体的并集)
```

### 🎬 多模态算法岗方向（面试加分）

**Q9: 项目如何扩展到多模态（图、表、文本）？**

A: **核心思路**：同域向量表示 + 统一召回

```
文本块      → BERT embedding → FAISS索引 ┐
                                           ├→ RRF融合 → Rerank → 生成
表格块      → 表格OCR→Markdown→embedding ┤
                                           
图片块      → CLIP视觉编码器→embedding ──┘
```

**关键技术点**：

1. **多模态Embedding**：
   - 用CLIP或BLIP将图片/文本投影到共享向量空间
   - 相同空间内混合检索

2. **表格处理**：
   - 表格OCR提取 → 转Markdown格式 → 保留表格语义
   - 表格本身+行文本并行索引

3. **生成侧**：
   - 大模型使用Qwen-VL或MiniGPT-4（支持多模态输入）
   - Prompt中附加"图片/表格来源"追溯

**增量工作**：
- paddleocr表格提取 (+2天)
- CLIP embedding微调 (+3天)
- Qwen-VL部署 (+2天)

---

**Q10: 表格密集文档（如对标表、参数表）的多模态方案？**

A: **专项方案**：
```
原始PDF表格
  ↓ pdfplumber提取
  ├→ 结构化为JSON  → embedding
  ├→ 渲染为图片    → CLIP编码
  └→ 转Markdown    → 文本embedding
  
三种编码方式并存，检索时：
  Query → 同时检索JSON、图片、文本三种embedding
      → RRF融合 → 返回表格完整内容+位置
      → 生成时"见表X行Y列"精确定位
```

**优势**：
- 表格参数对比查询 (Query带数字) → JSON完美匹配
- "展示H100和RTX4090对比" → 表格图片直接可视化
- 表格行表述变体 → 文本embedding覆盖
