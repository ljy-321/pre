# 面试高频 Q&A（含“多模态算法岗”定向问题）——带标准回答思路

你可以把下面的答案当作“模板话术”：先讲现象/原因，再讲你怎么做，再给指标或验证方式。

## A. RAG 系统通用高频（每题都给可直接复述的答案）

1. `Q：RAG 的整体流程是什么？`
   `A：切块（chunking）-> 建索引（向量 + BM25）-> 多路召回（Dense/BM25/融合）-> 重排（可选 reranker）-> 生成（带证据约束）-> 引用/拒答（阈值触发）-> 评测闭环（Recall/MRR/NDCG + badcase）。`

2. `Q：你怎么选择 chunk_size 和 overlap？`
   `A：做三组切块实验（例如 256/512/1024，overlap 50/100/200）。太小语义不完整导致 Recall@5 低；太大噪声增多或跨主题导致召回精度下降。最终选择能在 Recall@K 上最优且 badcase 最少的组合，并保证表格作为原子块不被切断。`
   （可套你的话术：`512+100 最优，Recall@5 最高`）

3. `Q：为什么你要做“表格保护”？`
   `A：企业技术文档表格往往承载关键参数（型号、尺寸、额定值）。固定长度切块如果切断表格行会造成列错位，embedding 与 rerank 都会错误匹配，直接导致答非所问。我把表格抽取为独立元素，作为原子 chunk，不进入常规文本切分。`

4. `Q：Query 理解怎么做？为什么不直接 LLM 改写？`
   `A：用轻量规则做同义词扩展 + BM25 自然覆盖部分关键词差异。LLM 改写成本更高、延迟更大且在企业 FAQ 场景里收益不一定划得来。轻量方案可以把“类型/形式/种类”“功率/容量/出力”等常见差异覆盖掉，召回率通常能提升（例如 +8%）。`

5. `Q：为什么要混合召回（Dense + BM25）？`
   `A：Dense 擅长语义相似，但对精确关键词/型号类问题可能漏召；BM25 对关键词匹配更稳。混合召回利用互补性提升召回。比如“基础类型/基础形式”这种同义表达，BM25 能覆盖关键词，“Dense”能覆盖语义，融合后 Recall@5 更稳。`

6. `Q：RRF 融合的直觉是什么？`
   `A：不同检索器的分数尺度无法直接比较，所以用“排名融合”。RRF 让多个来源都给出较好排序的文档更容易进入最终 TopK，且实现简单、对标定不敏感。`

7. `Q：重排器能带来什么提升？代价是什么？`
   `A：召回阶段用快模型取 TopN（如 Top20），重排用 Cross-Encoder 让 query 与 doc 做细粒度交互，把相关证据提到前面。通常准确率提升明显（例如 +14pp），代价是计算量大，所以重排只用于小候选集，避免影响延迟。`

8. `Q：怎么缓解幻觉？`
   `A：三板斧：Prompt 强制只基于 context；设置置信度阈值，召回证据不足就拒答；生成后做引用校验（可选进阶）。核心不是“让模型不要胡说”，而是“让它没有胡说的空间”。`

9. `Q：拒答机制怎么设计？阈值用什么？`
   `A：用最大召回/重排分数作为置信度代理；如果所有候选分数都低于阈值，直接返回“根据现有资料无法确定”。阈值最好通过评测集调参，而不是拍脑袋。`

10. `Q：你如何处理多文档冲突？`
   `A：在企业文档中版本差异可能导致冲突。我会在索引元数据里保留发布时间/文档版本（如果有），生成时把更可信/更新的证据优先；评测中也会加入冲突类 query 做专项观察。`

11. `Q：如果检索不到（空召回）怎么办？`
   `A：先做 Query 同义扩展或更换融合权重；如果仍然召不回，就拒答而不是编造，并把该 query 记录到 badcase 池，用于后续补充文档或调整词表。`

12. `Q：你怎么做延迟优化？瓶颈在哪？`
   `A：瓶颈通常在 rerank 和生成端。优化策略是先粗筛再精排（减少重排候选数），对热门 query 做缓存；生成端降低 max_tokens 或设置较低 temperature；索引端选择合适的 FAISS 索引结构。`

13. `Q：你怎么评测？为什么要有评测集？`
   `A：因为 RAG 的好坏不是看一次 Demo。评测集用 query -> gold chunk/doc，按事实/对比/汇总分桶，计算 Recall@K/MRR/NDCG，同时观察 badcase 分布，形成闭环迭代。`

14. `Q：为什么你选择 FAISS（而不是 Milvus）？`
   `A：数据量在几十万以内时 FAISS 简单、部署成本低；Milvus 更适合更大规模与分布式。我的项目在小规模场景里追求快速落地与可解释性，所以先用 FAISS，并在文档里写清楚数据量增长后的升级路径（如换 Milvus + HNSW）。`

15. `Q：Embedding 和 BM25 的本质区别是什么？`
   `A：BM25 是稀疏关键词匹配，依赖词项与词频；Embedding 是稠密语义表示，能捕捉同义语义，但对精确关键词/数字有时不如 BM25。混合召回就是用它们的优势互补。`

## B. 多模态算法岗定向（同样给标准回答思路）

16. `Q：多模态 RAG 里，视觉信息怎么进入“检索”阶段？`
   `A：两条路线：视觉 OCR/结构化抽取后把图表内容当作“视觉证据 chunk”（文本+表格）；或者直接用视觉-文本 embedding（图像 embedding + 文本 embedding）进行双塔检索。工程上建议先保证“可抽取与结构化”（OCR/表格理解），再做 embedding 联合检索与 rerank。`

17. `Q：如果图表是关键证据，你怎么保证表格数字不被 OCR 错读？`
   `A：用结构化抽取替代纯 OCR：识别表格行列边界，保留单元格位置；对关键字段做校验（数值格式、单位、范围约束）；必要时引入二次置信度判断，对低置信单元格触发人工确认或拒答。`

18. `Q：多模态 embedding 融合怎么做（早融合 vs 晚融合）？`
   `A：早融合把视觉和文本在网络中更早交互，效果上限高但训练成本大；晚融合先各自编码再融合（例如 concat/加权和/门控），更易落地且可解释。我的建议是：先从晚融合做 baseline，再根据错误类型迭代融合策略或加门控模块。`

19. `Q：如何处理多模态的“对齐问题”（图和文本不在同一语义空间）？`
   `A：用对比学习（contrastive learning）或跨模态匹配损失训练成共同 embedding 空间；同时在数据层做“弱监督对齐”（例如引用关系/标题-图注对齐）。在线阶段还可用 rerank 对齐最终证据。`

20. `Q：CLIP/BLIP/LLaVA 这类模型，你会怎么解释它们分别适合什么任务？`
   `A：CLIP 强在图文对比检索与零样本分类；BLIP 适合图像到文本生成或更通用的图文理解；LLaVA 属于视觉-语言对话框架，更适合“基于图像回答问题”。在 RAG 场景里，我会优先用“结构化抽取 + 检索”保证证据，再用视觉语言模型做证据汇总与问答。`

21. `Q：多模态 rerank 的输入怎么设计？`
   `A：Cross-modal rerank 可以用“query + 候选视觉证据（图/表） + 候选文本摘要”做联合打分；如果候选是 OCR 表格，rerank 输入可以直接是结构化文本（cell 序列化）+ query。实践中 rerank 通常在候选集很小（TopN）上运行。`

22. `Q：多模态检索评测怎么做？`
   `A：和文本 RAG 类似，构建 query -> gold evidence（图/表/截图或其文本化 chunk），计算 Recall@K/MRR/NDCG；同时按任务类型拆桶（表格问答/图像定位/同义追问），观察失败模式。`

23. `Q：如果你的多模态系统“答非所图”，你第一步怎么排查？`
   `A：先确认检索：候选 evidence 是否召回到正确图表；其次确认 OCR/结构化：表格是否被错读或错列；最后确认生成约束：是否只引用正确证据块。按链路逐段定位，避免直接怪模型。`

24. `Q：你如何把你这个“文本 RAG 项目”迁移到多模态算法岗？`
   `A：我会强调我已经做过“证据链工程化”：文档解析->结构化->混合检索->重排->评测闭环。这套证据链思想同样适用于多模态：把图表结构化成证据 chunk，做多模态检索与 rerank，再用生成端做证据汇总与拒答。`

25. `Q：如果让你设计一个多模态增强的“表格理解 + RAG”，你的 MVP 是什么？`
   `A：先做表格结构化抽取（行列/单元格）并把它序列化为可检索证据 chunk；实现图表证据的检索（文本化 embedding 或联合 embedding）；再在生成端强制引用证据并加置信度拒答。等 MVP 跑通后再升级到视觉语言模型做更细粒度问答。`

26. `Q：训练数据怎么获得？没有标注怎么办？`
   `A：企业场景常见“弱标注”：图注/标题/表格编号天然给出候选对齐；可以用检索生成 pseudo-label（hard negatives）做对比学习；同时把失败样本沉淀成后续标注优先级，提高标注效率。`

## C. 你在项目里要“怎么讲贡献”（带可直接用的答案）

27. `Q：面试官问“你做了什么”？你怎么回答？`
   `A：我主导了企业 PDF 到可检索证据的工程链路：表格保护 + 规则边界切块，完成向量索引（FAISS）与稀疏索引（BM25）；实现了 Dense/BM25 三路召回并用 RRF 融合，随后用可选重排提升候选质量；最后设计了自建评测集与 badcase 池做迭代，形成可解释的指标闭环。`

28. `Q：你怎么证明你的优化有效？`
   `A：用离线评测集量化：chunk 实验对比 Recall@K；召回融合对比纯向量与纯 BM25；重排对比“直接取 Top5”与“Top20->Rerank->Top5”；并用 badcase 分析根因（空召回/答非所问/幻觉/延迟高）验证修复策略。`

29. `Q：如果让你再做一轮提升，你优先做什么？`
   `A：优先改“证据质量”：强化 OCR/表格结构化的可靠性与证据 chunk 的一致性；其次做更精细的 Query 理解与重排阈值标定；最后做更快的推理与缓存优化，保证线上体验。`

30. `Q：你遇到的最难 bug/badcase 是什么？怎么解决？`
   `A：印象最深的是“空召回/答非所问”，典型原因是同义表达差异与 chunk 切断表格。我的修复是先做轻量同义词扩展提升召回，再把表格当作原子 chunk，同时在生成端增加拒答阈值，避免模型硬编。`
